# myx.distro-remote `--install`/`--manage` design (parked)

In-progress design thread for splitting `myx.distro-remote`'s stubbed `--manage` flag (and the related `--interactive`) into real verbs. Migrated from memory 2026-07-19 — was an in-progress design sketch, not a finished spec. The build-status conflict recorded below spun off a still-open re-verification against `ws-myx-devops`; this file holds the design reasoning/history.

`DistroRemoteConsole` (`myx.distro-remote/sh-scripts/RemoteConsole.fn.sh`) originally had two long-standing stubs, `--manage` and `--interactive`, both just `echo "not implemented yet"`. `--manage` also looked like a reserved `myx.distro-manage` package slot in `--start-{source|deploy|remote|manage}-console` — confirmed wrong, no separate manage package exists; source/deploy/remote each have their own `DistroXTools.fn.sh` and that pattern isn't duplicated for "manage".

## 2026-07-15: first grasp, not settled

Proposed splitting into two verbs:
- `--install` — bootstrap verb for a bare/unconfigured target. Working theory: reuse myx.distro-deploy's project-install pipeline (tar-over-ssh, `DeployProjectSsh.fn.sh` idiom) to push tooling, then run the target's own `DistroLocalTools`/`DistroXTools --install-distro-X` remotely.
- `--manage` — expects an already-configured target (same precondition as `--select-remote`). Open, unresolved: what does it do that plain `--select-remote` doesn't? (reconfigure? status check? re-sync?)

Ruled out: folding VM start/stop (provisioning) into `--manage`/`--install` (different system/risk profile, e.g. bhyve VM tooling); reusing `myx.common lib/remoteContext` directly (only an example of the injection pattern — real delivery primitive is myx.distro-deploy's own tar-over-ssh pipeline).

One more loose idea floated, not settled: maybe `--manage` is a *persistent context switch* (select a remote once, subsequent commands implicitly target it) rather than a one-shot verb. Design pass paused here at that point, no conclusion.

## 2026-07-16: both open questions grounded further, still not settled

Confirmed in code at the time: `--manage` and `--interactive` were still literal `echo "not implemented yet"` stubs. No `--install` case existed in `DistroRemoteConsole`'s dispatch at all — it would be new, not a rename of an existing stub.

**Open question 1 (`--install`'s pipeline)**: the codebase has *two separate, non-overlapping* SSH-target selection mechanisms — the earlier "reuse `DeployProjectSsh`" theory glossed over the gap between them:
- `myx.distro-remote`'s own registry (`DistroRemoteConsoleRemotes --upsert` etc.) — lightweight, just `SSH_HOST`/`PORT`/`USER`/`HOME`/`ARGS` keyed by a free-text remote name, stored in `remote/static/<name>.remote.env` (or the legacy `.local/MDLC.remote.settings.env`). No `project.inf`, not part of the distro project graph.
- `myx.distro-deploy`'s project system (`DeployProjectSsh.fn.sh`/`DeployProjectsSsh.fn.sh`) — operates only on *registered distro projects* that declare `deploy-ssh-target:`-style Provides in their own `project.inf`; ships prepared install files + exec script from `$MMDAPP/output/deploy/<project>` to the target via a base64(openssl/base64/uuencode)-over-ssh pipe.

  A name registered via `--remotes --upsert` is **not** automatically a distro-deploy project — reusing `DeployProjectSsh`'s pipeline for `--install` would require first promoting the ad hoc "remote" into a real registered project (its own `project.inf` + Provides). Still unresolved whether that promotion is the right shape or whether `--install` should instead bypass the project system entirely.

**Confirmed what "bare/unconfigured target" bootstrap looks like manually** — documented in `myx.distro-.local/sh-lib/help/Help.DistroLocalTools-install-unix-bare.help.md`: verify bash/git and `ssh -T git@github.com` access **on the target itself**, `mkdir -p .local/myx && git clone git@github.com:myx/myx.distro-.local.git`, then run `DistroLocalTools.fn.sh --install-distro-remote` (git clone/pull of `myx.distro-remote` into `.local/myx/myx.distro-remote/` plus `mkdir $MMDAPP/remote`). This is a "**target clones itself**" model requiring the target to already have its own GitHub SSH identity. Any `--install` automation has to pick one of two shapes: (a) ssh in and remotely run these same git-clone commands (preserves the target-has-its-own-GitHub-access precondition), or (b) push an already-fetched tree via the `DeployProjectSsh` base64-over-ssh technique (avoids requiring target-side GitHub access, but hits the project-registration gap above). Neither was confirmed as the intended direction.

**Open question 2 (`--manage` vs `--select-remote`), hypothesis**: `DistroRemoteTools.fn.sh` (the remote-side tooling entrypoint, distinct from `RemoteConsole.fn.sh`) already has one-shot maintenance verbs — `--upgrade-remote-tools` (re-runs `--install-distro-remote` on the target) and `--make-console-command` (regenerates the `DistroRemoteConsole.sh` launcher). `--manage` could plausibly mean: SSH-execute one of these verbs against an already-registered remote, reusing `DistroRemoteConsoleStartSelectedRemote`'s existing SSH plumbing but targeting `DistroRemoteTools.fn.sh <verb>` instead of `DistroRemoteConsole.sh --start-*-console`.

## 2026-07-16 second pass: evidence tilts toward option (a)

Re-read `RemoteConsole.fn.sh`, `DistroRemoteTools.fn.sh`, `RemoteTools.Make.include`, `DistroLocalTools.fn.sh`, and `myx.distro-remote/project.inf` line by line.

- `myx.distro-remote/project.inf` declared no `Requires`/`Augments` on `myx.distro-deploy` (only `Augments: developer-sdk:recommended`). Option (b) (reuse `DeployProjectSsh`) would introduce a cross-package dependency that doesn't exist today, on top of the project-registration gap. Option (a) needs no new dependency — it's remote-executing existing `DistroLocalTools.fn.sh --install-distro-remote` logic: clone `os-myx.common`, clone `myx.distro-.local`, clone `myx.distro-remote`, `mkdir -p remote`, then `DistroLocalTools --make-workspace-integration-files` → `DistroRemoteTools --make-console-command`.
- Wrinkle on the "target needs its own GitHub SSH identity" precondition: the registry's `SSH_ARGS`/`useSshArgs` field (wired through `DistroRemoteConsoleRemoteOption` → `DistroRemoteConsoleStartSelectedRemote`'s `ssh $SSH_ARGS -p ...`, and separately `DistroSshConnect` in `myx.distro-deploy/sh-lib/lib.distro-image.include`) is documented in `myx.distro-deploy/README.md:53` and `myx.distro-source/README.md:88` as accepting `-o ForwardAgent=yes -o AddKeysToAgent=yes`. Forwarding the *operator's own* agent through `SSH_ARGS` could satisfy the bare-target's GitHub-access need instead of provisioning a separate deploy key. Caveat: no code path sets `ForwardAgent` automatically today — it would have to become explicit `--install` design (e.g. default `SSH_ARGS` to include it, or document as an operator precondition), and forwarding the operator's own GitHub identity onto a bare/unaudited box is a real trust-model change needing explicit sign-off, not a silent default.
- Confirmed `DistroRemoteTools --make-console-command` is real, matching the `--manage` hypothesis. `console-remote-bashrc.rc` puts both `myx.distro-remote/sh-scripts` and `myx.distro-.local/sh-scripts` on `PATH` for interactive sessions, and `RemoteConsole.fn.sh` already supports a `--non-interactive` mode piping stdin into a bash sourcing that same bashrc — so an SSH one-shot `DistroRemoteTools` verb invocation could ride this existing non-interactive entry point.

## 2026-07-17: open question 2 DECIDED, open question 1 reopened wider, then parked

**Decided**: `--manage` = SSH-execute a `DistroRemoteTools` maintenance verb (e.g. `--upgrade-remote-tools`, `--make-console-command`) against an already-registered remote — one-shot, distinct from `--select-remote`'s interactive console session. User confirmed this shape.

**Open question 1 got bigger, not smaller.** User doesn't want to just pick (a) or (b) — wants `project.inf` to declare specs on what to push/bring/share/prepack in deploy data, and separately floated that `--manage` (interactive) may need to carry more than a bare SSH session: bring an installer/settings bundle along, the way `lib/remoteContext` already does for some other flow, and possibly relevant actions too. Also raised: `ShellTo` may want an analogous interactive-with-brought-context mode. None of this is scoped — a wider design surface than the original (a)/(b) framing.

**User's explicit call: park this entirely for now** — "we need to talk on it again — when other stuff is finished... there is much more to plan while we can't implement new project due to tonns of unfinished ones." Blocked behind clearing the existing backlog of unfinished projects first, not a "revisit tomorrow."

**Status at park time**: `--manage` semantics settled, safe to build on. `--install`'s mechanism is more open than before — `project.inf`-declared bundle specs, remoteContext-style installer/settings carrying, and a possible `ShellTo` interactive-context mode are all new surface, none scoped. Don't resurface this design thread for active work until the user reopens it. If asked "what's blocking distro-remote `--install`", answer with this state, don't re-derive from scratch.

**Note on later build status**: the retired `TEAM-STATUS.md` recorded `--manage` as "BUILT for real" (2026-07-18, checked against `ws-2017` not `ws-myx-devops`) — but a re-check of `RemoteConsole.fn.sh` under `ws-myx-devops/source/myx/myx.distro-remote/sh-scripts/` on 2026-07-17 found `--manage`/`--interactive` still literal `echo "not implemented yet"` stubs, and no `--install` case in the dispatch at all. These two claims conflict, and the conflict is still unresolved — whoever picks this up re-verifies current code state against `ws-myx-devops` before trusting either.
